# Database schema (`@workspace/database`)

## Role in the architecture

The SurrealDB schema and its permission contract, split by database: `schema/common` holds
what every database has, `schema/directory` the directory database (accounts, organisations
and memberships) and `schema/tenant` the database of one organisation (`t_<key>`). A
database's schema is the common files and then its own, each set in file name order. Comment
annotations above each table (`-- @region`, `-- @replicate none`, `-- @id`, `-- @crdt`,
`-- @owner`, `-- @can`, `-- @readonly`) tell the modeling stage how the table replicates, which
id prefix its keys use and who may write it. The same schema is applied to the local replica
and to a server, and the replica schema generated from it is the one description of replicated
tables that every runtime reads. Notes carry their write rules there: a member creates notes and
edits or deletes only those it wrote (`-- @owner author`), an admin edits or deletes any note.
A field marked `-- @readonly` is set by a device only when it creates the record; after that
only the gateway's own writes change it (the profile's email through the confirmation flow).

## Key exports

- `schema/common/`: `contract-values.gen.surql` (the contract's length limits as database
  parameters, one `<value>_max_length` for each value with a limit, generated by `bun run model`
  from the kernel's `CONTRACT_VALUES`; the length asserts of the profile's name and bio, the
  organisation's name and the note's text name them instead of writing the number),
  `fn::entity_id` (record keys in the workspace id format) and the replica's
  own tables (`_replica_snapshot`, `_replica_update`, `_replica_outbox`, `_replica_projected`,
  `_replica_peer`, `_replica_head`, `_replica_cursor`: snapshots, the update log numbered
  without gaps, the outbox, projected records, the identity each Loro peer of a region writes
  as (bound at its first accepted batch), the pull cursor; a number is unique per region in the
  log and the outbox; on a device `_replica_head` also holds the region's generation, which a
  reset of its local copy moves), closed to every record user and never replicated.
- `schema/directory/`: the account tables, Better Auth's models and its two-factor and passkey
  plugins', written only by the gateway as its namespace user and never replicated: `identity`
  (an account: its email, kept and matched in lower case, so an address in any case is one
  account, the account's own name and `locale`, the language it signed up in, which its mails
  speak until its settings name one, `en` when nothing named one, and whether its second factor
  is on; an identity reads only its own row), `account` (how an identity signs in: the credential
  row holds the argon2id hash of the password), `device_session` (one row per sign-in of a device
  of an identity, with the device's own id, its label and the session token it holds; a sign-out
  ends the row, which stays listed for 30 days; with the function `fn::devices_signed_in_with`,
  the devices an identity is signed in on with one device more, by which the gateway judges the
  limit of devices), `verification` (one-time tokens with an expiry,
  a sign-in's two-factor challenge and a passkey's ceremony among them, each ceremony marked with
  its kind, `ceremony`, which the schema derives at each write, and indexed by kind and expiry, so
  the gateway reclaims the expired ones of a kind reading them alone), `two_factor` (an account's second factor: its
  key's secret and its backup codes, encrypted, and whether a code confirmed the key, with the
  functions `fn::two_factor_challenge_end` and `fn::two_factor_challenges_end`, which end one
  pending two-factor challenge or every one of an identity) and `passkey` (an account's passkeys:
  each credential's id, unique, its public key and its counter), all but `identity` closed to
  every record user; their reference columns hold the identity's key as a string, as Better
  Auth's adapter writes it. The product
  schema defines no access method, so no record user signs in to a server. Then `profile` (its
  owner reads it; only the gateway writes it, through replication; a name is not empty,
  an email is an address, and a name and a bio hold at most the lengths the contract states,
  `$profile_name_max_length` and `$profile_bio_max_length`), `settings` (an account's settings, today its language and its theme, one row per identity in
  its private region; its owner reads it, only the gateway writes it, through replication),
  `tenant` (an organisation: its key of lowercase letters, digits and underscores, at most
  `$organisation_key_max_length` characters, its name (at most `$organisation_name_max_length`
  characters), namespace, database and status; closed to every record user), `membership` (an
  identity's role in an organisation, `member` or `admin`; an identity reads only its own rows,
  and only the gateway writes them) and `invitation` (the pending invitations of an email to an
  organisation: the role the account takes on accepting, who invited it, the token its link
  carries and its expiry; one per organisation and email, the email kept in lower case; closed
  to every record user, written by the gateway only).
- `schema/tenant/`: `member` (a member of the organisation keyed by the identity id, with its
  role; server-only) and `note` (the organisation's notes in the `tenant` region, each naming
  its author member, a text of at most `$note_text_max_length` characters; only the gateway reads or
  writes it on the server).
- `./replica-schema`: `replicaSchema`, every replicated table with the region whose
  documents hold it and the field kinds the replica needs. Generated by `bun run model`
  into `src/replica.schema.gen.ts`, so every runtime that replicates reads the same one.
- `tests/suites/*.toml`: SurrealKit suites, run on one ephemeral database that holds every
  schema folder: the permissions of `identity` (with `account`), `profile`, `settings`,
  `membership` (with `tenant`), `device_session`, `invitation`, `two_factor` and `passkey`, the
  structure of the tenant
  tables (`tenant-structure`), the kind of ceremony each row of `verification` is marked with
  (`verification-ceremony`), and the generated suites of the shapes.
  `setup.surql`, which SurrealKit runs in each test database before it applies the schema,
  defines a record access method `identity` for that database only: the suites' record actors
  sign up and in through it, which creates the identity row and its credential row as the
  gateway does; the product schema has none;
  `tests/anonymous`: the unauthenticated-client check over raw HTTP.
- `src/model-contract.spec.ts`: holds the schema to the contract's model
  (`contract/domain/model.schema.json`). Each entity has its table, its fields, region, id
  prefix, crdt and read-only fields, owner and abilities, and a unique index for each unique
  set, and the `ASSERT` of each field states the limits the kernel's generated values
  (`CONTRACT_VALUES`) give the field (enum members, `minLength`, `maxLength`, `format: email`,
  `pattern`), no more and no less; the values are held to the contract by their own spec, in the
  ahead mode as they were at the branch's base or head, so this spec needs no contract of its
  own to follow a business commit. In the same mode an entity the model declares now and did not
  declare at the branch's merge base waits while the schema defines no table of its name
  (`src/__fixtures__/entities-ahead.ts`, with its spec), so a business commit may add an entity
  before the implementation adds its table, which is then held like any other; on `main` and in
  `bun run check` (which drops the ahead mode even when the shell exports it) every entity is
  held. An upper length bound is the parameter of a contract value, never a number, except on
  the two columns that hold no value (`device_session.device` and `.label`, listed in the spec);
  `tenant.key` and `tenant.name`, which no model field states, are held to the platform values
  `organisation-key` and `organisation-name`.
  It reads the schema as an embedded database reports it, so it needs no stand.
- `src/assert-limits.ts` and `src/length-bounds.ts`: what the spec reads an `ASSERT` with
  (`readAssert`: its limits, the parameters it names, the length bounds it writes as numbers) and
  the length-bound check (`lengthBoundProblems`: a number where a parameter belongs, a listed
  column that writes none, a parameter that is undefined, backs no value or holds another number),
  each with its own spec of the refusals.

## Commands

- `bun run typecheck`, `bun run lint`.
- `bun run test`: the unit spec (`vitest.unit.config.ts`), no stand needed.
- `bun run test:db`: SurrealKit suites and the anonymous check against the stand at
  `SURREAL_URL`, which `bun run test:db` at the repository root sets through `mcproc exec` from
  the mcproc manifest (the `surrealdb-e2e` app, `http://127.0.0.1:8010` in the main checkout).
- `surreal db validate 'database/**/*.surql'`: syntax check without a database.
