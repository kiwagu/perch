# Contract reference
Generated by `bun run contract:schemas` from the describe texts of the engine's schemas and its registry of rules: never edit it by hand.

A key is written as its path from its file's root, `<name>` standing for any name of a map; its anchor is the file and the path in lower case (`#screen-anchors-name-secret`), and a rule's is `rule-<id>`.

## Screen file

One screen of the application.

### `id`

<a id="screen-id"></a>
A screen name of the vocabulary: one or two kebab-case segments.

### `title`

<a id="screen-title"></a>
The title of the screen, for a reader.

### `description`

<a id="screen-description"></a>
What the screen is for: the task it serves and when it is shown, in one or two sentences, so an agent chooses the screen before reading its anchors. Not a list of its parts: each anchor has a description of its own. At most 200 characters.

### `frame`

<a id="screen-frame"></a>
The frame around every screen: it has no route of its own.

### `bindings`

<a id="screen-bindings"></a>
The routes of the screen: at least one unless the screen is the frame.

### `bindings.path`

<a id="screen-bindings-path"></a>
The route path: static segments, `$param`, `{-$param}` (optional) and `$` (splat), from `/`.

### `bindings.guard`

<a id="screen-bindings-guard"></a>
Where an account the route is not for is sent: a guest to sign-in (`authenticated`), or a signed-in account to the profile (`guest`); absent: nobody is sent.

### `bindings.roles`

<a id="screen-bindings-roles"></a>
The roles the route serves: it opens for an account that holds one, after the guard and before the search is read, and the not-found screen opens at the same address for any other.

<a id="screen-anchors-name-description"></a>

### `anchors.<name>.roles`

<a id="screen-anchors-name-roles"></a>

### `anchors.<name>.own`

<a id="screen-anchors-name-own"></a>
Shown to a member only on the entries the member owns.

### `anchors.<name>.holdsInput`

<a id="screen-anchors-name-holdsinput"></a>
Left out, every field (input, textarea, select, checkbox, radio, switch) holds input, except one whose own change applies it at once and nothing else applies it: one of its bindings runs an action that takes the field itself and that no other anchor of the screen runs with it, or its own event moves its screen's search with it (a navigate to a path of its screen whose search takes the field) and no other anchor's event moves there with it. A field a submit button runs the action with, or a search button moves the search with, holds input.

### `anchors.<name>.marksState`

<a id="screen-anchors-name-marksstate"></a>
The field shows no state colour: its border keeps the untouched colour whatever its `data-state`; for a field where fresh input is the point (an entry form). Left out: the field shows it.

### `anchors.<name>.secret`

<a id="screen-anchors-name-secret"></a>
A field that holds a secret (a password, its confirmation, a current password): it never leaves the page but in the request of the action that takes it, so no navigate carries it into a search and no search parameter starts it; only a secret input renders a `visibility-button`.

### `anchors.<name>.codes`

<a id="screen-anchors-name-codes"></a>
The data-code values the element carries. An error that leaves them out carries the codes of the failures of the actions the anchors of its part bind (`<part>.<name>` beside `<part>.error`), each once, `failed` last.

### `anchors.<name>.ranked`

<a id="screen-anchors-name-ranked"></a>
A message whose codes are in rank order: of the codes raised before it shows, it shows the first, and the others go with it; a clear of it, in any flow, takes away every code raised before it. Only a message of two codes or more, each once.

### `anchors.<name>.fields`

<a id="screen-anchors-name-fields"></a>
An error's codes, each with the field of the screen it concerns, which the error shows under and marks invalid; a code left out concerns the form. Left out, each code a field of the model gives goes to the control the binding passes for that field, unless two bindings pass two controls.

### `anchors.<name>.fields.<name>`

<a id="screen-anchors-name-fields-name"></a>
A declared anchor: 2 to 4 dot-separated kebab-case segments, kind last.

### `anchors.<name>.dataId`

<a id="screen-anchors-name-dataid"></a>
What the data-id of the element holds: the id of the entity it shows.

### `anchors.<name>.dataValue`

<a id="screen-anchors-name-datavalue"></a>

### `anchors.<name>.states`

<a id="screen-anchors-name-states"></a>

### `anchors.<name>.derived`

<a id="screen-anchors-name-derived"></a>

<a id="screen-anchors-name-source-params"></a>

### `anchors.<name>.source.params.<name>.search`

### `anchors.<name>.source.paged`

<a id="screen-anchors-name-source-paged"></a>
The list shows one page of the action's entries: the page and the size the route's search parameters `page` and `size` name; it derives `range`, `previous-link`, `next-link` and `size-select`, which holds no input: its element carries `holdsInput={false}`.

### `anchors.<name>.composite`

<a id="screen-anchors-name-composite"></a>
The platform composite the field opts into (`password-rules`): the loader derives its list and items on the screen, `<screen>.<list>` and `<screen>.<list>.<item>-item`; only a secret input opts in.

### `anchors.<name>.confirm`

<a id="screen-anchors-name-confirm"></a>

### `states`

<a id="screen-states"></a>

### `flow`

<a id="screen-flow"></a>
The flow of the screen: an XState v5 machine config, which may write a transition as its target, an effect by its name and a region by its pattern or its button, and leave out the region of a button bound to one action; the loader expands it into the config `createMachine` takes.

### `flow.id`

<a id="screen-flow-id"></a>
The id of the machine: a one-segment name the flow declares, which the app gives its machine, and an id target `#<id>.<state>` names (one segment, as XState splits a target on `.`); absent, the app names the machine by the screen id.

### `flow.description`

## Rules

### Language

<a id="rule-language"></a>
The page renders `en` on the stands, and its wording is not part of the contract. Assert `data-code` (`contract.codes`), `data-state`, `data-id` and `data-value`, never text; the only text a test reads is text it entered itself.

Keys it concerns: [`manifest.contract.instructions.language`](#manifest-contract-instructions-language).

### Sessions and platform actions

<a id="rule-session"></a>
Every scenario starts in a fresh browser context with nobody signed in (`guest`). What a platform action does is read from `platform.actions.<name>`, the platform file: its `description`, its `result` (what holds once it succeeds), its `codes` (what a failure shows), its `changes` (written on every action, `[]` where it changes none: the reads whose answer, for the organisation, the account and the params it ran with, differs once it succeeds, platform actions a list, a section or a table takes as its `source`) and, when it sends mails, its `mail` and its `notices`; never assume it from the action's name. One account per browser: a second account, or a second device of the same one, needs a browser context of its own.

Keys it concerns: [`manifest.contract.instructions.session`](#manifest-contract-instructions-session).

### Reading the screens

<a id="rule-screen-map"></a>
`screens` lists every screen once. Its `id` is the screen name its anchors start with; its `title` is what a reader calls it and its `description` what it is for. `bindings` are its routes in the router's format (TanStack): `path` with static segments, `$param`, `{-$param}` (optional) and `$` (splat); `guard` (`guest` or `authenticated`: where an account the route is not for is sent, a guest to sign-in or a signed-in account to the profile); `roles` (the roles it serves: the router serves it only to an account that holds one, after its `guard` and before it reads the search, and opens the screen of the binding at `/$`, the not-found screen, at the same address for any other); `params` and `search` as flat JSON Schemas; `history` (`push` or `replace`); `retain` (search parameters kept across navigations); `example`, a deep link to the route with fake data, written as the router writes a link: each path parameter at its first `examples` value, every search key at its `default`, else its first `enum` value or example (the app's own links leave out a value equal to its default and reach the same state). `frame: true` marks the frame around every screen, which has no route. Every binding `path` is a TanStack Router path in the router's own syntax, `params` are its path parameters and `search` its search parameters, and a route is a state address: the same path with the same search reaches the same state after a reload. `entry` lists the anchors present once the screen is open; some are alternatives by state, so wait for the one the state shows. `anchors` maps each declared anchor to its `kind`, `binding`, `codes` (its `data-code` values), `fields` (an error's codes, each with the field it concerns, which the error shows under and marks invalid), `dataId` (what its `data-id` holds), `dataValue` (it or its options carry a `data-value` of `contract.choiceValues`), `states` (its `data-state` values), `derived` (the suffixes it renders as `<anchor>.<suffix>`), `roles` (who sees it, among the roles its screen's bindings serve; absent: every role of the screen), `own` (shown only on the entries the member owns), `ranked` (a message whose `codes` are in rank order: of the codes raised before it shows, it shows the first, and the others go with it; a `clear` of it, in any flow, takes away every code raised before it), `secret` (a field that holds a secret, a password: it never leaves the page but in the request of the action that takes it, never into an address and never filled from one) and `source` (where a list's entries come from: a platform action, which the list reads each time it starts to render after it did not, each time the organisation or account it reads for becomes another or a search parameter it reads does, and where a flow says `read`, with `params` (each a search parameter of the route, `{ "search": "<name>" }`, or a constant) and `paged: true` (one page of the action's entries: the page and the size the route's search parameters `page` and `size` name; the list derives `range`, whose `data-from`, `data-to` and `data-total` say which entries the page shows of how many, `previous-link` and `next-link`, each only where there is such a page, and `size-select`, whose options carry the action's `paged.sizes` and choose the route's `size`, which writes no `x-perch`; the select holds no input, so its element carries `holdsInput={false}`; a paged list has at most 3 segments, as its options add two to its name); or an entity of the model, which it follows as the stored data changes). A screen's `states` say what each container state shows, and its `wireframe` is the default state as a Playwright aria snapshot. A screen's `flow` is an XState v5 machine config: `initial`, `states` with `on` (an event is the user acting on that anchor, typing included for a field, a platform event of `platform.events`, or a data event `model.<entity>.<field>`: the stored value of a field the screen shows changed, here or on another device), `target`, `guard` (a name of `meta.guards`), `actions` (effects `show`, `clear`, `read` and `navigate`: `clear` empties a field of the screen, a secret one included, so it holds no input any more, as if nothing was typed, and makes an anchor that carries codes show none until one is shown again; `read` makes a list of the screen whose `source` is a platform action read that action again and show its entries once the read is in, the app taking them from the answer of the action that just ran when it returns them; such a list also reads it each time it starts to render after it did not and each time the organisation or account it reads for becomes another or a search parameter it reads does, and a navigate that sets a search parameter a paged list reads says `page: 1`; one whose `source` is an entity follows the stored data and is never read; a navigate's `search` gives each key a literal, `{ "anchor": "<field>" }`, the value that field of the screen holds when the app moves, or `{ "item": "<item>" }`, the `data-id` of the entry of that item or row whose control the user acted on, a control (a button, a link, a tab or a field) in the item's part (`<part>.<name>`) on whose event the navigate runs; an item or a row as a value of `params` or `input` gives the `data-id` of the entry whose control acts, likewise), `invoke` (a model or platform action with its `input`, whose values are as a binding's `params`, `onDone`, `onError`; `read: false` on an invoke says nothing reads after its action, which changes nothing a list of the screen shows, and `read: false` on one branch of its `onDone` or `onError` says nothing reads after that outcome, where another branch reads; never both, never beside a `read` of the same branch, never on the transition of an event; after an invoke that does not say `read: false`, every branch of its `onDone` reads each list of the screen with a platform source that its action may change, or says `read: false`: a list one of whose entries its `input` takes, one whose source's `params` take a value its `input` takes, and one whose source its action's `changes` names; a failure holds no read, so an `onError` reads where it says), `type: final`, and `meta.address` on a state a route reaches. A state of the root may be `type: parallel`: its `states` are regions, the screen's independent areas, all active at once, each with its `initial` and its plain states; a target of the root may name a region's state as `<parallel>.<region>.<state>` (the other regions start at their `initial`), a target in a region names a state of that region or, by the flow's `id` (a one-segment name the flow declares, which the app gives its machine), a state of the root as `#<flow id>.<state>`, which leaves the parallel state and enters that state afresh, and within a parallel state an event is handled by one region or by the state's own `on`, never by two. A state's `meta.renders` names anchors of the screen that only some states render: an anchor no state of the flow lists is rendered in every state, one that a state lists is rendered only in the states that list it, a state of a region rendering what its parallel state lists too; the anchors nested under a listed one (`<anchor>.<rest>`, such as the items of a list) are rendered with it, or where they are listed themselves. Rendered means visible to the user: an anchor a state does not render is absent from the page or hidden on it. A guard of `meta.guards` is a sentence saying when it holds, or `{ "codes": [<code>, …] }`, which guards only a branch of an invoke's `onError` and holds when its action failed with one of those codes. Carry it into `setup({ guards, actions, actors }).createMachine(flow)` unchanged, implementing the guards it names, the four effects and an actor per `invoke.src`; an invoke's `read: false`, or a branch's, is a statement of the contract, nothing the machine runs. A control whose anchor is an event of the flow (a button, a select, a switch) is enabled exactly while a state the machine is in handles that event (`snapshot.can`), and disabled otherwise: a Save disabled while it saves is the flow saying so, never a flag of its own. A `visibility-button` (`<input>.visibility-button`, the eye of a secret input, in `contract.derivedParts`) shows what the input holds as typed, or hides it again: presentation only, it is never an event of a flow and always enabled, and its `data-value` names what a click does, `show` or `hide`. `ids` holds the same anchors flat, each with its screen. On a development or e2e build, `window.__perch.ui.anchors()` lists the anchors the page renders now, with their attributes and visibility. `composite` on a secret input names the platform composite it opts into (`platform.composites.<name>`): the screen's `anchors` then hold its list and items, each marked `derivedFrom` with the composite and, for an item, its name; they are declared anchors like any other.

Keys it concerns: [`manifest.contract.instructions.screenMap`](#manifest-contract-instructions-screenmap).

### Field states

<a id="rule-field-states"></a>
A field carries `data-state` `unsaved` while it holds input no save has taken; one whose `fieldStates` lists `saved` carries `saved` once a save stored what it shows, while it stays on the screen; a field carries no `data-state` otherwise.

Keys it concerns: [`manifest.contract.instructions.screenMap`](#manifest-contract-instructions-screenmap).

### Bindings

<a id="rule-bindings"></a>
`{ "model": "<entity>.<field>" }` shows or edits `model.$defs.<entity>.properties.<field>`. `{ "action": "<entity>.<action>" }` runs an action of `model.$defs.<entity>.x-perch.actions`; `{ "action": "platform.<name>" }` runs `platform.actions.<name>`. Its `params` name, per parameter, the anchor whose value it takes, a constant `{ "value": ... }`, or `{ "search": "<name>" }`, the value of that search parameter of the route the screen was opened at. An action of `platform.actions` that sends a mail declares it under `mail`: `to` (the parameter whose value it goes to, or `account`: the email of the account the action acts on, the signed-in account for an action on its own account, else the one its parameters name, whoever is signed in), `language` (a parameter holding a language, `account`, or `recipient`: the account whose email the mail goes to, else the signed-in account) and `link` (the `screen` its link opens and the `search` parameter carrying its token); a scenario names it `[mail:<action>]`. Its `notices` are mails that only tell, with no token, each with its `name`, `to` (a parameter, or `account`: the email of the account the action acts on, as it was before the action changed anything), `language` and, optionally, a plain `link` to a `screen` whose routes need no parameter; a scenario names one `[notice:<action>.<name>]`. `{ "route": "/path" }` navigates to the path of a binding of some screen. `{ "search": "<name>" }` on a field starts it with the value of that search parameter of the route the screen was opened at and gives it that value again each time the parameter becomes another, which the user may change; it may sit in a list beside the action the field gives its value to. A list of bindings runs in its order, or one of them by the mode of the screen; the `flow` says which. An anchor with `asks` asks the frame's confirmation (`asks.dialog`, with `asks.code`) before its action runs: the app's platform gate opens it, confirm runs the action and cancel does not; a screen builds no dialog of its own for it. An anchor with `leaves` is a control whose flow moves to another screen: the app's platform gate asks the frame's leave question (`leaves.dialog`) before its event while one of the fields of `leaves.loses` holds unsaved input, leave goes on and stay does not; the fields the move carries in its search are not among them. A button's action `params` are the union of the params the fields of its part pass for that action, a param the screen writes on the button winning; an error's `codes`, unless the screen writes them, are the failures of the actions bound beside it and invoked against it by the flow, plus the codes the flow shows on it, `failed` last; an invoke without `onError` whose action fails with codes clears its part's error on entry and, back in the one state that entered it on a control, shows the failure there (a start state, one several states enter, or one a platform or data event enters, writes its `onError`), and an `onError` written as its target alone still shows the failure on that error, on the screen's error when no control enters and the input names no field.

Keys it concerns: [`manifest.contract.instructions.bindings`](#manifest-contract-instructions-bindings).

### Reading the model

<a id="rule-model"></a>
`model` is the data model: a JSON Schema 2020-12 document with one `$defs` entry per entity. An entity's `x-perch` says its `table`, its `region` (`private`: the account's own data; `tenant`: the current organisation's), its `id` prefix, its `owner` field, `can` (per role, the actions allowed on any entry or only on its own), its `actions` with their parameters and their `changes` (written on every action, as a platform action writes it), and `unique` and `index`. A field's `x-perch` says whether it is `readonly`, the entity a `record` points at, and its `crdt`: how concurrent edits merge (`text`, `list`, `counter`, or `none` for the last writer).

Keys it concerns: [`manifest.contract.instructions.model`](#manifest-contract-instructions-model).

### Reading the activities

<a id="rule-activities"></a>
`activities` are the activities across screens, one file each in `contract/domain/activities/<id>.yaml`, carried here verbatim: which screens form one task, in which order, and what the task carries from one screen to the next. An activity has an `id`, a `title`, a `description` (what it is for), the `roles` that take part and `data` (what it carries, by name, each with a `description` and, when it is a field of the model, its `model` as `<entity>.<field>`). The rest is an XState v5 machine config in the subset of the flows, without effects or `invoke`: `initial`, `meta.guards` and `states`, where a state is a visit to a screen: `meta.screen` names the screen (one screen may be visited by several states), `meta.address` the `path` of a binding of that screen (the activity is where its address is), and `type: final` ends the activity. A state's `on` maps an anchor of its screen or of the frame to where acting on it leads: `target` (the next visit), `guard` and `description`. The activity says where a task leads and the screens do the work: after that anchor, the flow of its screen navigates to the target's address, or the anchor is a link to it (`binding.route`). Carry each into `setup({ guards }).createMachine(activity)` unchanged, as the flows, implementing the guards it names; a scenario that walks an activity names it in its `activity`.

Keys it concerns: [`manifest.contract.instructions.activities`](#manifest-contract-instructions-activities).

### Reading the scenarios

<a id="rule-scenarios"></a>
`scenarios` are the end-to-end scenarios in the spec-instruction shape, authored as Markdown files in the e2e tree (`tests/e2e/scenarios/<entity>/<layer>/[<area>/]<slug>.md`: a YAML front matter with `tags`, an optional `activity`, `devices` and `data`, then the sections `# <title>`, `Where:`, `## Scenario:`, `### Steps` and `### Expected result`) and carried here parsed. Their fields: `id` (the file's path under `tests/e2e/scenarios/` without `.md`, `<entity>/<layer>/[<area>/]<slug>` with the layer one of `base`, `flows`, `features`; the test is `tests/e2e/src/<id>.e2e.spec.ts`), `title`, `tags` (`smoke` or `full`), `activity` (the id of the activity of `activities` it walks, when it walks one), `devices` (a letter per browser with the role it reaches by the end; every device starts as `guest`), `where`, `data` (`generate` or a fixed value), `scenario`, `steps` and `expected`. Brackets in their text reference the contract: `[<anchor>]` (in `ids`, or derived from one with a suffix of its `derived`), `[/path]` (a route of `screens`), `[code:<code>]`, `[state:<state>]`, `[value:<value>]`, `[mail:<action>]` (a platform action that declares the mail it sends) and `[notice:<action>.<name>]` (a notice of that name the platform action declares). They are the contract's feedback loop: a scenario that cannot be written from the contract alone (an anchor, a code, a state, a route or a role it would need) names a gap to fix in the contract files, never one to work around in a test.

Keys it concerns: [`manifest.contract.instructions.scenarios`](#manifest-contract-instructions-scenarios).

### Contract gaps

<a id="rule-contract-gaps"></a>
When the contract cannot say what you need (a state, a region, an event, a value, a route, a role, a code, a shape), stop at that part: build what the contract covers and report a contract gap with your result, as four lines: `Contract gap:` what is needed; `Facet:` which part of the contract cannot say it (the model, a screen file, the platform, the flow subset, an activity, the scenario grammar, a check); `Emulation refused:` the workaround you did not build; `Proposal:` the change to the contract and its cost. Never hold it in the app or in a test instead: state in a component for a flow state or a region the contract lacks, a value or a route it does not carry, an anchor or a code born in the code or in a test. An emulation is a fork of the model that no check sees and the next build from this manifest loses; the contract is changed first. The one transient state a component holds is whether a password input shows what it holds, which the `visibility-button` the contract declares on it toggles.

Keys it concerns: [`manifest.contract.instructions.gaps`](#manifest-contract-instructions-gaps).
